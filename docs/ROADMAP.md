# Robot War Engine — Revival Roadmap

_Last updated: 2026-09-11. Status of the codebase is as of the `revival` integration branch (upstream `master` @ b2d8a31 + merged fork work, see Phase 0). Run `rwe_test` for the current suite size -- see CLAUDE.md for why it is not recorded here._

## Where the project stands

- **Engine:** ~93k lines of C++20 under `src/` (~49k when this branch started), deterministic sim at 30 ticks/s, OpenGL 3 renderer, COB VM, A* pathfinding, lockstep multiplayer over the internet. Loads original TA data (HPI/GAF/3DO/COB/TDF/TNT/OTA) and the GOG release's Smacker movies.
- **Launcher:** Electron 22 / React 16 / Redux lobby + master server + `rwe_bridge` IPC.
- **History:** Michael Heasell (2017–2023, ~1,950 commits) — the engine, the format parsers, the COB VM and the deterministic simulation. Kevin Hake modernised the build in March 2026 (Boost removed, C++20, SDL3, CI green). Taylor Gunnoe added hotkeys / speed / pause / Phase‑1 AI in April 2026 (unmerged upstream until now).
- **First public pre-release 2026-09-10.** Upstream's only tag is `v0.1.0` (2017); this branch tags `v1.0.0` ("Bot bot boom boom v1.0", under the main-menu title — B4 for short, being four B’s), `v1.1.0-pre1` and now `v1.1.0-pre2`, all three on the fork as well as locally. The first two have no release behind them; the third does — Windows installer, Windows zip and Linux AppImage at <https://github.com/CubeB/RWE-B4/releases> (see Phase 0). The CMake version is derived from git tags, and only from annotated ones.

## Guiding principles

1. **Determinism is load-bearing.** Anything that influences the sim lives in `sim/`, uses `SimScalar`/`simulation.rng`, no wall-clock or unordered iteration. Every merged feature must keep `rwe_test` and the `GameHash` sync checks green.
2. **Data-driven first.** TA data dictates UI screens and unit behaviour; prefer implementing what the FBI/TDF/GUI files already describe over inventing new config.
3. **Small, mergeable PRs against a green CI.** The March‑2026 CI matrix (gcc‑14, clang‑18, MSVC 2026, MinGW64, Debug+Release) is the gate.
4. **Personal project, for now.** No upstream coordination or outreach is planned. The forks by Kevin Hake, Taylor Gunnoe and Oskar Pedersen are reference material — check them before starting a feature so their work isn't redone.

**Matching the original.** A lot of Phase 1 has come from disassembling `TotalA.exe` rather than guessing at behaviour. The findings — addresses, constants, algorithms, and the places RWE deliberately differs — are consolidated in [`docs/TOTALA-EXE.md`](TOTALA-EXE.md), now a hundred sections numbered up to §102 (83 and 84 are not there), with the probe scripts that produced them in [`tools/exe/`](../tools/exe/). Three subjects grew large enough to want documents of their own: aircraft *attack* behaviour — the mission table, the bomber run, the strafing pass, the gunship pendulum — in [`docs/TOTALA-EXE-MISSIONS.md`](TOTALA-EXE-MISSIONS.md); the shaded unit rasterizer in [`docs/TOTALA-EXE-SHADING.md`](TOTALA-EXE-SHADING.md); and where a wreck comes from and why one over water sinks in [`docs/TOTALA-EXE-WRECKS.md`](TOTALA-EXE-WRECKS.md). Read them before reimplementing anything that is meant to look or feel like TA; several plausible-sounding readings of this binary are wrong in ways that only show up when you replay the arithmetic. The shading decode is the cautionary tale — it was read twice and corrected four times, and each correction came from replaying the pipeline over a real `.3do` rather than from arguing about the listing.

## Phase 1 — Playable single-player skirmish loop (≈ 2–3 months)

Goal: a full game vs. no opponent feels like TA — every basic order works, UI is complete enough that a player never needs the F10 debug menu.

**Orders & unit behaviour**
- [x] Reclaim features: the merged branch only ran a timer. Now work = metal + energy at `workerTimePerTick` per tick, resources credited progressively, feature deleted and `featureReclamate` spawned on completion; progress lives on the feature so several builders can share it. Tested at sim level and through `tick()`. Closes the "corpses clog the battlefield" note from the 2022 blog post.
- [x] Reclaim units (own or enemy, in range): work = `buildTime`, payout = build cost × fraction actually built, progress on `UnitState` (hashed + dumped), dies without wreck or explosion (`DeathType::Deleted`). Tick-driven test covers a builder reclaiming an enemy solar.
- [x] Reclaim polish, mostly (2026-09-05, `TOTALA-EXE.md` §97). The `seqNameReclamate` swirl was already playing on `FeatureReclaimedEvent`; that half of the entry was stale. **`autoreclaimable` is now honoured**, and the entry's premise was wrong about where it belongs: `0x47EA40`, the area scan that reads the bit, has exactly two callers in the whole binary — the ground `RepairPatrol` handler and `VTOL_RepairPatrol` — so automatic reclaim is a patrol behaviour, and TA has no area-reclaim command and no idle-builder sweep at all. RWE's patrol sweep now skips `autoreclaimable=0` features (the two fortification walls, which a builder would otherwise eat), searches out to the unit's own `SightDistance` instead of a hardcoded 256, keeps the original's two candidates — nearest metal and nearest energy — and follows its four store comparisons, so a builder with full storage walks past the wreck field and one short of energy goes for the trees. `src/rwe/sim/autoreclaim.test.cpp`. The reclaim sound landed 2026-09-10 (`e69ec4d3`) — see the Sound completeness entry below. **Still to do:** the info-panel progress bar, which is UI work (fork issue #19).
- [x] Repair: `RepairOrder` heals at the build rate (free, as in TA) or finishes an unfinished unit; REPAIR panel button, repair cursor mode, and left-click-on-damaged-friendly for builders. Also fixed `buildExistingUnit` checking `isBeingBuilt` against the builder's definition instead of the target's.
- [x] Patrol: `PatrolOrder` loops through waypoints (re-queued on arrival), engages enemies in primary-weapon range en route unless on hold fire; PATROL button + `cursorpatrol` sprite; a single click patrols between the point and the unit's position.
- [x] Capture: `CanCapture` now parsed from FBI; `CaptureOrder` works like repair but accumulates `captureProgress` on the target and swaps owner at `buildTime`, clearing its orders/targets; `UnitCapturedEvent` drops it from the old owner's selection. CAPTURE button + `cursorcapture`.
- [x] Resurrect, implemented 2026-09-06 (`TOTALA-EXE.md` §98). The corpse-to-unit mapping is a string operation rather than a table -- the feature's own name truncated at the first underscore -- so `armsolar_dead` and `armsolar_heap` both give `armsolar`. `(BuildTime * 0.3) / (WorkerTime/30)` ticks, the one job of the three that scales with the builder; the unit returns complete, facing the way its corpse lay, on one hit point. Draws the nanolathe while it works. Still mod-only: no shipped FBI names `CanResurrect`. One departure in §88 -- the corpse is removed before the unit is placed, because a corpse is `blocking` and RWE refuses an occupied footprint.
- [x] **Capture progress goes with the captor** (2026-09-05, `TOTALA-EXE.md` §96). Asked for as a decay; the original has nothing to decay, because capture progress was never on the thing being captured. The Capture mission counts up in its own order record (`mission+0x36`, total in `+0x3A`) and the target unit has no capture field at all — so cancelling the order frees the count with it, re-ordering starts from zero, and two captors on one target race rather than pool. RWE's `CaptureOrder` now carries the pair the same way and `UnitState::captureProgress` is gone from the struct, the hash, the save and the dump. The clock came with it: `trunc(E*0.015 + M*3/14 + 150)` ticks, capped at 1800, scaled by `(hp+max)/(2*max)` and by `kills/5 + 10` tenths — so a damaged unit changes hands faster, a veteran one slower, and **the captor's `workertime` is not in it anywhere**: capture is one tick of work a tick for everybody. A nanoframe cannot be captured ("That unit is a cloud of vapor"), which RWE was allowing. `src/rwe/sim/capture.test.cpp`.
- [x] Transports (load/unload, `TransportCapacity`, `TransportSize`): first version landed 2026-08-28, see play-test round 2 below.
- [x] Self-destruct: `Ctrl‑D` starts a 5 s countdown (toggle again cancels), the sim detonates the unit with its `SelfDestructAs` weapon (new FBI field, falls back to `ExplodeAs`), no wreck; seconds remaining drawn above the unit. Blink/flash effect not yet done. The blink is fork issue #29.
- [x] COB getters: Health, VeteranLevel, MinId/MaxId/MyId, UnitTeam, UnitBuildPercentLeft, UnitAllied etc. were implemented in the merged `feats/next` work. Remaining FIXMEs (UnitTeam returning player id, UnitAllied = same owner) need a team/alliance model — tracked under multiplayer.
- [x] Pathing: units slow when climbing (top speed → ½ at the slope limit, floor ¼) (#45); ground steeper than half the slope limit is rough terrain for routing (#33); no diagonal squeeze between touching obstacle corners (#30); an unreachable move target ends at the closest reachable point and the order completes instead of re-pathing forever (#28). Metal prints at one decimal place and energy at none, because the format strings are `"+%.1f"`/`"-%.1f"` against `"+%.0f"`/`"-%.0f"`, and all four are clamped at zero before formatting. Kills appear under the damage bar — no rectangle of their own; the routine takes DAMAGEBAR's left edge and its bottom plus two — as `1 kill` / `3 kills`, gaining `- Veteran` from the fifth, which is the whole of TA's veterancy display. The mission line is not composed anywhere: every mission record carries a display name at its `+0x00` and `0x439DF0` fetches the one for the current mission, so RWE transcribes both tables (`Standby`, `Moving`, `Nanolathing`, `Under construction`, `Annihilating`, …) and joins its orders to them. - [x] **Focused-control highlight (#5) and list-box selected-item brightness (#6)** (2026-09-05, §99). Both turned out to be one read of the gadget renderer. The only comparison against the panel's focused-gadget index anywhere in it is in the text-box draw, which puts a one-pixel vertical caret at the end of the text in interface colour 9 (light blue) — buttons and list boxes show no focus at all, so the caret *is* the highlight. RWE drew an underscore whether the box had the focus or not, and `UiPanel::focus()`/`unfocus()` had their tests inverted, dereferencing an empty optional. The selected list row is brightened by running its rectangle through `PALETTE.LHT` at level 30 — measured at a median 1.84x on luminance, applied after the text so the text brightens too — where RWE washed it with 12% white and you could barely see it. The same call greys a control at `PALETTE.SHD` level −20 (0.82x). **The three gadget-renderer details §99 left owing are all in as of 2026-09-10** (§19, §99). *Greying* had in fact landed on 2026-09-02 and both documents were stale on it: a disabled `UiStagedButton` draws the greyed frame the artists put one past the pressed frame in the button's own GAF, rather than running the rectangle through SHADE row 12 — the two agree because the artwork was drawn to agree, not because the code does the same sum, and only a mod whose GAF carries no such frame can tell them apart. *The caption drop shadow*: only for a gadget whose attribs carry bit 3, which `0x4A59A4` tests and the first port missed; the shipped menu buttons do not set it, so they have none (corrected 2026-09-11 after a play-test against the original, `2fc621c0`). *The quick-key underline*: where the gadget's `quickkey` character appears in its caption, a one-pixel line goes under it in interface colour 2, GUIPAL green, (0, 128, 0) on screen, not in the caption's colour, one row below the height of the font's `I`, its offset and width measured in the font's own per-glyph advances by `findCharacterInText`. That match is case-insensitive and has to be — RWE has folded the gui file's key to an SDL keycode by the time a button holds it — which is also the better reading: four shipped gadgets are authored in the other case (MISSION.GUI's `SELECT` against `Select Mission`, and the three `UNDO` buttons against `Undo Changes`) and would lose their underline to an exact test. The same pass wired the main menu's Credits button to `5.zrb`; see the movies below. `src/rwe/UiRenderService.test.cpp`.

- [x] **How the original orders what it draws** (disassembled from `TotalA.exe`, 2026-08-31). There is no depth buffer at the world level at all: TA is a pure 8-bit software painter and everything — terrain, units, features, shadows, particles — goes through the same three blit routines in call order, last one wins. The world render function is `0x468cf0`. Objects are bucketed by **world Z alone, quantised to 16 units** (`0x4697ed`), ignoring height entirely even though the projection is `screenY = z − y/2`; within a bucket there is no secondary sort. (`sortbias` is parsed from the FBI into `unitdef+0x21a` but read nowhere — dead in this build.) Particles are not in that list at all: they live in a separate manager with **ten hard-coded layer buckets**, and each SFX type is hand-placed in one — wakes on 2, weapon impacts on 6, **VTOL and thrust exhaust on 7**, damage smoke on 9 (over everything, including health bars). So particles are not uniformly in front or behind; each effect is placed by hand.
  **Why the Atlas exhaust sits under the aircraft in the original**: explicit layering, not depth and not the spawn position. Layer 7 is drawn at `0x469b38`, and the very next pass at `0x469b3d` draws every object whose `occupy != GROUND` — airborne units get their own late pass, so the aircraft is blitted over its own exhaust a few instructions later. Had it been on the ground the exhaust would have landed on top of it. RWE reaches the same result by a different route (depth testing against world Y, which is what its camera uses for depth); the two agree for an airborne aircraft, and differ only in that RWE will also let a tall ground unit in front occlude the plume, which TA would not. Judged the better behaviour for a renderer that has a real depth buffer, so kept.
- [x] **How the original does fog of war, and how terrain affects it** (disassembled from `TotalA.exe`, 2026-08-31). The grid is **32 world units per cell**, two heightmap samples across — which RWE already matches. Three states come from two arrays: one global *explored* array of `uint16` used as a bitmask, one bit per LOS group, set-only; and a per-player *visible* array of one byte per cell used as a **reference count** of how many of that player's units see it. `UpdateUnitLOS` (`0x4827b0`) runs per unit per tick but is **incremental** — it early-outs unless the unit changed cell (or, in terrain mode, moved its eye by more than 5), then subtracts the old stamp and adds the new one.
  Sight comes from FBI `SightDistance` (`unitdef+0x202`). There are three modes, exposed in the skirmish GUI as **Permanent / True / Circular**, defaulting to **True**. Circular mode does not ray-trace at all: it blits a hand-drawn mask sprite from `anims/vismasks.gaf`, ten frames of radius 5 to 14 cells, so sight is `clamp(SightDistance/32, 5, 14)` cells and saturates at 448 world units. True mode walks a **fixed fan of authored rays read from `gamedata/los.tdf`** (`TABLE1`..`TABLE9`, each a list of stepped `dx,dy` runs replicated into four quadrants) with a running maximum-slope horizon — shadow casting, not a per-cell retrace — and its radius is capped at **8 cells, 256 units**, because the table index is `min(sight/32, numtables-1)` with `numtables=9`.
  Terrain occlusion uses its own grid holding **two heights per cell**: `max(seaLevel, (2·max+min)/3)` decides whether a cell is *revealed* and `max(seaLevel, (max+2·min)/3)` decides whether it *occludes*, so it deliberately errs toward revealing. The eye is `clamp(unit Y, ≥ seaLevel+1) + the model's own height` (the maximum vertex Y of its 3DO, not an FBI field). The horizon is only raised on cells the ray actually revealed, so once a ray is blocked the horizon stops rising. Water is flat ground at its surface.
  **Radar has no grid at all** — it is a per-tick unit-versus-unit range query with `range = RadarDistance + 2 × altitude`, terrain never blocks it, and it flags units rather than revealing ground.
  Drawing is **marching squares over cell corners**, not per-cell blocks: an overlay grid records which of the four surrounding cells are dark, and each 32×32 screen tile picks one of 14 authored frames from `anims/fog.gaf` (`Black1..4` and `Gray1..4`, 14 frames each), with the variant chosen as `(cellX + cellY + scroll) & 3` so the ragged edge is fixed in world space and does not shimmer when scrolling. Fully-unexplored tiles are a solid palette fill. The ragged boundary is in the artwork, not in a shader.
- [x] **Fog of war rebuilt to match the original** (2026-08-31). The grid is now indexed in the projected space TA uses — cell row `(worldZ − terrainHeight/2)/32`, one shared helper so the renderer cannot drift from the simulation. Sight walks the authored ray fan from `gamedata/los.tdf` (parsed through the VFS, with generated fans as a fallback so a sim with no game data still sees) with the running maximum-slope horizon that only rises on cells it actually revealed, and the radius is capped at 8 cells / 256 world units as the table count forces. Fog is drawn from TA's own artwork: `anims/fog.gaf`'s `Black1..4`/`Gray1..4`, 14 frames each, picked by a marching-squares corner code with the variant fixed in world space at `(x+y)&3`, rasterised into a single-channel texture at one texel per world unit.   Two things came back different from the plan, both for good reasons. The quadrant replication of the ray tables is **90° rotations, not sign flips**: measured on the real `los.tdf` at radius 8, rotations cover the disc exactly while sign flips leave ten holes along the east–west axis, and the tables are authored to tile that way (each fan's first ray runs up the +y axis and its last stops one cell short of +x). And the fog raster is **windowed on the camera** rather than covering the map: at one texel per world unit a whole 640×640-cell map would be 400 MB, past most drivers' limits, so it holds a 2.6 MB window a few tiles larger than the view — which is what the original does anyway, composing its overlay per visible screen tile. A full window rebuild costs about 1 ms, a typical fog change 0.37 ms with only the dirty sub-rect uploaded.

- [x] **Shading, the exact table** (2026-09-08). The row was already the original's; what a row *meant* was a curve. `PALETTE.SHD` stores palette INDICES from a nearest-neighbour search, so a row does not scale a colour -- it snaps the scaled colour back onto the 256 entries that exist. A census of the shipped table says how far that is from a multiplier: at row 31 it leaves **eight** of the 256 entries exactly where they were and puts **fifty-eight** of them on white, where the fitted curve claimed a uniform 1.807x for every one of them, and row 15 is the identity for 232 of them. The texel's own palette index now rides through the texture atlas in a second single-channel copy, and the fragment reads `SHD[row * 256 + texel]` out of a 256x32 image of the table -- the original's inner loop entire (`0x4C81A4`-`0x4C81BD`): one shift, one add, one byte load, no second mask, no clamp, no blend between rows. Flat-coloured polygons come with it, since the original's own flat filler at `0x4C0B10` indexes the same table with the polygon's colour index standing in for a texel.
  Two things were measured before any of it was written, and one of them killed the obvious implementation. **The generator is exact**: `0x4BADF0` transcribed into C++ reproduces the shipped `palettes/PALETTE.SHD` byte for byte from `PALETTE.PAL` -- 0 of 8192 bytes differ -- so a data set missing the file has the table rebuilt from its palette rather than falling back to a curve, and that transcription is what `src/rwe/ShadeTable.cpp` ships. And **the cheap version does not work**: expressing the lookup as a per-texel ratio applied to the mipmapped colour, which would have kept the atlas's own filtering for nothing, loses the value on 431 of 24576 channels with a worst case of 119/255 across 38 palette entries -- a channel that is zero before the row cannot be scaled into one that is not. So the colour is read from the table and the atlas's filtering has to come with it: the index atlas carries a mip chain built by plurality vote, because GL's box filter would average indices and the mean of two palette indices names a third colour that is nowhere between them. `src/rwe/ShadeTable.test.cpp` pins the reader, the generator against an exhaustive nearest match, and the image.

A suspended search is re-checked against the unit before it is resumed and dropped if the unit died or was given a different order. A save **carries** it, in five integers: a search is a pure function of the world, the goal and the cell it started from, and only the last is lost (the unit keeps walking its straight-line stand-in while it waits), so the save writes that footprint and the expansion count and the load rebuilds the search and runs it forward that far — exactly, because A\* is deterministic. Dropping it on both sides instead would have passed the saved-game test and broken replays, whose keyframes go through the same path during playback against a recording that dropped nothing. The scratch cell went from eight bytes to twelve: the static asserts that made its int16 indices safe were bounded by the cap that is gone. Two new cases in `pathing.test.cpp` pin it — a search cut into one-expansion slices returns the route an uninterrupted search returns, and a goal walled off on a 64×64 map comes back exhausted after four thousand expansions where it used to stop at a thousand with the open list still full. **The budget is deliberately left at 4000 a tick**; raising it is the separate entry in Phase 5, and moving both at once would make neither measurable. **And `path_bench`'s obstacles were broken all along** — an immobile unit definition with no yard map, an assert in Debug and an empty-optional dereference in Release — so every figure it produced before this date was measured with obstacles that did not reliably obstruct, and none of them is a valid baseline. It has a yard map now.
- [x] **A unit that overshoots a waypoint turns round and goes back for it** (2026-09-10, #36, `TOTALA-EXE.md` §102). The question the entry asked first — whether the original does anything of the kind — has an answer, and it is not the one the twenty-waypoint clamp hinted at. **The original turns round too.** `0x43CD20` has no skip-ahead and no passed-the-plane test: a unit that gets past the corner it was heading for without coming within five world units of it still has that corner as `wp[1]`, and the aim point drags it back. So #36 is a proposal to improve on TA, not a bug report against it. What the original has that makes it rare is the two things RWE was missing either side of that: it keeps the corner the unit came *from*, so the aim point is a point on the segment eighty world units ahead of the unit rather than the corner itself — a corridor, which pulls a unit that has drifted sideways back onto the line before the corner ever arrives — and it decides throttle with two brake tests rather than a cosine, accelerating only while the aim point is further off than twice the distance the turn will take (`distToAim > 2·speed·|err|/turnrate`) and while there is still stopping distance to the waypoint after next, braking at `brakerate` on any tick either fails. Three of those are now in, in that order: `pathToWaypoints` keeps the start cell and `PathFollowingInfo` starts at `begin() + 1`, `followSegment` projects the aim point, and the two tests replace `seek`'s speed factor in the original's own operation order — divide first, square after, because where that division truncates decides which tick the braking starts on. The straight-line stand-in is two points now as well, the unit's position and the goal, and it is walked on the tick the order arrives rather than the one after. The fourth thing, the original's five-unit advance radius, was tried and **backed out**: RWE keeps sixteen, and eight for the last waypoint. Five is fine for a unit on its own and costs about a third of the arrivals in a crowd, because a waypoint is a cell centre and a unit two cells across cannot always reach within five of one another unit is standing on — measured on `path_bench` at a hundred units, five arrived 27 and asked for 884 searches where sixteen arrived 49 and asked for 509. With the other three in and sixteen kept, that benchmark arrives 49 where the old follower arrived 45. `sim/pathfollowing.test.cpp` pins the three properties on real FBI numbers — an ARMFLASH slows into a right-angle corner, an ARMPW twenty units off its line is back on it before the corner, and neither ever takes a step with a negative component along the segment it is walking, which is the #36 assertion and which failed at -0.77 world units a tick on the follower this replaces.

- [x] **A crash writes a report** (2026-09-06). Until now a fatal fault killed the game in silence: the top-level catch in `main.cpp` only ever saw thrown `std::exception`s, and a segfault walked straight past it, so recovering anything meant reproducing the fault a second time under `tools/crash-catch.cmd` — which had to have been started beforehand. `src/rwe/util/CrashHandler.*` installs handlers for the fatal signals (and, on Windows, the unhandled-exception filter, `SIGABRT` and `std::terminate`, because `abort()` bypasses the filter) and writes `rwe-crash-<timestamp>.txt` next to `rwe.log`. It carries a backtrace and the context that says which crash this was: the phase of the frame, the scene, the map, the scene tick, the game time and the unit count, from four relaxed stores a tick. Everything below the install obeys the signal-handler rules — no allocation, no locks, no `std::filesystem`, and explicitly *not* the logger, whose mutex the faulting thread may be holding — which is why the path is formatted at install time and the report is built by a bounded appender into a static buffer. POSIX gets a `sigaltstack`, without which the stack overflow this most wants to catch could not be reported at all. ## Phase 5 — Performance, renderer, platform (ongoing, low priority until Phase 1 done)

The simulation half of this phase was brought forward and largely done — see "Eight hundred units at 36fps" in Phase 1, and `battle_test` and `RWE_ENABLE_SIMPROF` for how to measure the next round. What follows is what is still open.

- [x] Renderer profiled and cut, 2026-09-05. `RWE_ENABLE_RENDERPROF` (`src/rwe/render/render_prof.h`, the same shape as `RWE_ENABLE_SIMPROF` and off by default) breaks the frame down by phase; `battle_test` at 400 a side on Coast To Coast, Release, 1280x800, is what it was measured on. **The 23 ms claim did not survive contact with the profiler.** At 800 ground units the renderer was 29.8 ms a frame and the simulation tick 4.2 ms — the sim work had taken the tick from 25 ms to 4, so the renderer was not merely the largest cost but nearly the whole of it. At 800 *hover* units the largest cost was neither: 130,000 live wake dots cost 10 ms a tick in `updateParticles` and 12.9 ms a frame to draw. What the breakdown named, and what came of it:
  - Piece transforms were looked up by name — a `toUpper()` allocation and a hash lookup per link of the parent chain, per piece, per unit, per frame, and again for the shadow pass. `GameMediaDatabase::getUnitModelRenderInfo` resolves a model's hierarchy, meshes and rest transforms once. 17.7 ms → 5.0 ms.
  - Nothing was culled. `ViewCullTest` drops units, mesh features and their shadows whose model cannot reach the view (orthographic projection, so the test is a transform and four comparisons). 10,400 piece draws → 2,750.
  - Wake dots were all built and uploaded, on screen or not: 770,000 vertices, 18 MB a frame. Culled at the point they become geometry, and the batch's storage kept between frames. 12.9 ms → 4.0 ms, and per vertex 23.5 ns → 15.1 ns.
  - `updateParticles` asked `MapTerrain::getHeightAt` — a vertical ray cast against up to sixteen heightmap triangles — whether each wake dot had reached the shore. Every height that query can return lies between the lowest and highest corner of the cells it looks at, so a dot over water is settled by sixteen byte comparisons and the ray is only cast near a shore. 10 ms a tick → 3.6 ms.
  - Net: 800 ground units 34.0 ms → 16.7 ms a frame (29 → 60 fps, now on the 60 Hz vsync cap, with the world render itself down from 28.1 ms to 5.1 ms); 800 hover units 84.9 ms → 26.4 ms (11 → 38 fps).

Batching unit meshes by texture (#16) is still not done and is worth doing once something other than draw-call count is the limit — at 2,750 piece draws the unit pass measures 0.17 ms, so it is not the limit today.

Not for readability in the end but because the translation unit had outgrown what a COFF object can describe: 11,466 template instantiations, 46,124 sections against a signed-16-bit ceiling of 32,767, and the assembler switching the object to `pe-bigobj` without a word. The MinGW64 CI runner's binutils could not read that format back and dropped every COMDAT definition while keeping the references — a Debug-only link failure, 1,124 undefined symbols out of one object, every one a template or a lambda, while Release passed because the optimiser folded them away. Two more cuts followed on 2026-09-09, both of code that is dense in the way that costs sections rather than merely long. `GameScene_debug.cpp` took the parts no game ever reaches — `battle_test`'s standing battle and the F10 panel's unit spawner and placer — and `GameScene.cpp` went from 18,267 sections to 15,644. `GameScene_menu.cpp` took the F2 panel and everything behind it: the Resume/Options/Restart/Exit flow, the confirmations, the PREFS composite and every control wired to it, and the save and load dialogs with their list; `_commands` went from 26,721 to 21,981, from 82% of the ceiling to 67%, and is still the largest. Eight files now, beside the older `_util`. **What the measurement says, and it is the reason to stop here rather than keep cutting:** the count is a budget rather than a free win, because the standard library's floor is paid once per translation unit — the menu cut added 8,365 sections in total to take 4,740 off the peak. Where a new file lands is decided mostly by its includes: `_debug` came out at 4,839 with a tight list, `_menu` at 13,105 because it genuinely needs `MainMenuScene.h`, `LoadingScene.h` and `SaveFile.h`.

**The Ctrl hotkey block is done by one mechanism, not twenty features.** Most
of #131–#152 ask for a specific letter to select a specific kind of unit —
Ctrl+K for kbots, Ctrl+N for naval, Ctrl+Y for torpedo bombers. The original
does not have twenty selections: `0x4963e0` formats `"CTRL_%c"` and matches it
against the unit's FBI **Category** field (§74), and the shipped data defines
exactly six such tokens — `CTRL_W`, `CTRL_V`, `CTRL_F`, `CTRL_B`, `CTRL_R`,
`CTRL_P` — plus `CTRL_C` for the Commander. "Every other Ctrl+letter looks up
a category that no shipped unit has and selects nothing. A mod can invent
`CTRL_X` and the key springs to life." RWE implements the mechanism, so every
one of those letters already works for any data set that defines the token,
and none of them needs code. #131 (Ctrl+A), #145 (Ctrl+S), #152 (Ctrl+Z) and
#132 (Ctrl+D self-destruct) are separate features and are each implemented in
their own right.

**#126 (Ctrl+B cycles idle construction units) is refused, not deferred.** The
issue says so itself: "Functionality of modified OTA / demo recorder". In the
original Ctrl+B is the `CTRL_B` category selection — *all* construction units
at once — and that is what RWE does. Implementing the cycle would mean giving
a key a behaviour the original does not have and taking away one it does.
Recorded here rather than in §88 because it is a divergence from an *issue*
rather than from the binary. #133 (Ctrl+F cycles idle factories) is the same
mistake about the same mechanism and has the same answer.

**#125 is done in the part that is the original's.** Control groups are
implemented on the digits, the arrangement §75 decodes. The rest of that issue
is ProTA's rather than TA's — a sound on assignment, the squad number drawn
under the health bar, a factory adding what it builds to its own squad — and
is not planned.

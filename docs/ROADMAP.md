# Robot War Engine — Revival Roadmap

_Last updated: 2026-09-23. Status of the codebase is as of the `revival` integration branch (upstream `master` @ b2d8a31 + merged fork work, see Phase 0). Run `rwe_test` for the current suite size -- see CLAUDE.md for why it is not recorded here._

## Where the project stands

- **Engine:** ~121k lines of C++20 under `src/` besides ~51k of tests (~49k in all when this branch started; re-counted 2026-09-22, this line having said ~93k for long enough to be wrong), deterministic sim at 30 ticks/s, OpenGL 3 renderer, COB VM, A* pathfinding, lockstep multiplayer over the internet. Loads original TA data (HPI/GAF/3DO/COB/TDF/TNT/OTA) and the GOG release's Smacker movies.
- **Launcher:** Electron 22 / React 16 / Redux lobby + master server + `rwe_bridge` IPC.
- **History:** Michael Heasell (2017–2023, ~1,950 commits) — the engine, the format parsers, the COB VM and the deterministic simulation. Kevin Hake modernised the build in March 2026 (Boost removed, C++20, SDL3, CI green). Taylor Gunnoe added hotkeys / speed / pause / Phase‑1 AI in April 2026 (unmerged upstream until now).
- **First public pre-release 2026-09-10.** Upstream's only tag is `v0.1.0` (2017); this branch tags `v1.0.0` ("Bot bot boom boom v1.0", under the main-menu title — B4 for short, being four B’s), `v1.1.0-pre1` and now `v1.1.0-pre2`, all three on the fork as well as locally. The first two have no release behind them; the third does — Windows installer, Windows zip and Linux AppImage at <https://github.com/CubeB/RWE-B4/releases> (see Phase 0). The CMake version is derived from git tags, and only from annotated ones.

**Next, of the large things** (2026-09-22): **the AI on water and fragmented maps**, which is Phase 2's biggest remaining cluster and is really one problem wearing four entry titles -- the base built on ground its own army cannot leave (the commander's movement class wades deeper and climbs steeper than its constructor's, and `baseAnchor` is never revised), the sea ferry that retried one impossible landing 1426 times in a single game, no hovercraft at all, and naval doctrine. Each of those entries already carries its measurements, so the work is ready to start rather than needing a diagnosis first. Phase 3 is the next whole phase after it, and Phase 3 has begun (2026-09-23): desync diagnostics and drop handling are done, and so is the dependency that was sitting in Phase 2 -- an AI player in a network game no longer desyncs, its command timing having stopped being a function of anything local. What is left of Phase 3 is the launcher's half, and less of it each day: lobby archive matching, in-game chat and the dependency refresh are done, which leaves a public master server -- now obligatory rather than optional, the refresh's socket.io 4 having cut the launcher off from upstream's socket.io 2 one. Rejoining a game after being dropped (#188) is done as of 2026-09-23, engine and lobby both.

## Guiding principles

1. **Determinism is load-bearing.** Anything that influences the sim lives in `sim/`, uses `SimScalar`/`simulation.rng`, no wall-clock or unordered iteration. Every merged feature must keep `rwe_test` and the `GameHash` sync checks green.
2. **Data-driven first.** TA data dictates UI screens and unit behaviour; prefer implementing what the FBI/TDF/GUI files already describe over inventing new config.
3. **Small, mergeable PRs against a green CI.** The March‑2026 CI matrix (gcc‑14, clang‑18, MSVC 2026, MinGW64, Debug+Release) is the gate.
4. **Personal project, for now.** No upstream coordination or outreach is planned. The forks by Kevin Hake, Taylor Gunnoe and Oskar Pedersen are reference material — check them before starting a feature so their work isn't redone.

**Matching the original.** A lot of Phase 1 has come from disassembling `TotalA.exe` rather than guessing at behaviour. The findings — addresses, constants, algorithms, and the places RWE deliberately differs — are consolidated in [`docs/TOTALA-EXE.md`](TOTALA-EXE.md), now a hundred and three sections numbered up to §105 (83 and 84 are not there), with the probe scripts that produced them in [`tools/exe/`](../tools/exe/). Three subjects grew large enough to want documents of their own: aircraft *attack* behaviour — the mission table, the bomber run, the strafing pass, the gunship pendulum — in [`docs/TOTALA-EXE-MISSIONS.md`](TOTALA-EXE-MISSIONS.md); the shaded unit rasterizer in [`docs/TOTALA-EXE-SHADING.md`](TOTALA-EXE-SHADING.md); and where a wreck comes from and why one over water sinks in [`docs/TOTALA-EXE-WRECKS.md`](TOTALA-EXE-WRECKS.md). Read them before reimplementing anything that is meant to look or feel like TA; several plausible-sounding readings of this binary are wrong in ways that only show up when you replay the arithmetic. The shading decode is the cautionary tale — it was read twice and corrected four times, and each correction came from replaying the pipeline over a real `.3do` rather than from arguing about the listing.

## Phase 1 — Playable single-player skirmish loop (≈ 2–3 months)

Goal: a full game vs. no opponent feels like TA — every basic order works, UI is complete enough that a player never needs the F10 debug menu.

**Orders & unit behaviour**
- [x] **What earns a unit its veterancy** (2026-09-15, §5, fork #50). The reload term at `0x49E468` — `reloadTicks = ((120 - 20*hp/maxdamage) * ((100 - 6*tier) * reloadtime / 100)) / 100` — was already ported as `computeReloadTicks`; re-reading the branch confirmed it to the instruction, and the priorities note was simply stale about it. What was actually wrong was the *input*. Two tests stand in front of the kill counter at `0x4869CA` and RWE failed both: the victim must be finished (`0x4869A7` against its build progress) and the attacker's player must differ from the victim's owner (`0x4869BA` against the owner byte at `victim+0xFF`), so **friendly fire earns no veterancy** — shooting your own units was a way to farm the +30% damage of §5 and the −30% reload of §21, and is not — and neither does flattening a half-built nanoframe. The player-level Kills and Losses the end-game chart shows were left alone in this pass, their increments hanging off the death-cause jump table at `0x486E64`; that table was read next, and the entry below settles them. `sim/damage.test.cpp`.
- [x] Reclaim features: the merged branch only ran a timer. Now work = metal + energy at `workerTimePerTick` per tick, resources credited progressively, feature deleted and `featureReclamate` spawned on completion; progress lives on the feature so several builders can share it. Tested at sim level and through `tick()`. Closes the "corpses clog the battlefield" note from the 2022 blog post.
- [x] Reclaim units (own or enemy, in range): work = `buildTime`, payout = build cost × fraction actually built, progress on `UnitState` (hashed + dumped), dies without wreck or explosion (`DeathType::Deleted`). Tick-driven test covers a builder reclaiming an enemy solar.
- [x] Reclaim polish, mostly (2026-09-05, `TOTALA-EXE.md` §97). The `seqNameReclamate` swirl was already playing on `FeatureReclaimedEvent`; that half of the entry was stale. **`autoreclaimable` is now honoured**, and the entry's premise was wrong about where it belongs: `0x47EA40`, the area scan that reads the bit, has exactly two callers in the whole binary — the ground `RepairPatrol` handler and `VTOL_RepairPatrol` — so automatic reclaim is a patrol behaviour, and TA has no area-reclaim command and no idle-builder sweep at all. RWE's patrol sweep now skips `autoreclaimable=0` features (the two fortification walls, which a builder would otherwise eat), searches out to the unit's own `SightDistance` instead of a hardcoded 256, keeps the original's two candidates — nearest metal and nearest energy — and follows its four store comparisons, so a builder with full storage walks past the wreck field and one short of energy goes for the trees. `src/rwe/sim/autoreclaim.test.cpp`. The reclaim sound landed 2026-09-10 (`e69ec4d3`) — see the Sound completeness entry below. **Still to do:** the info-panel progress bar, which is UI work (fork issue #19).
- [x] Repair: `RepairOrder` heals at the build rate (free, as in TA) or finishes an unfinished unit; REPAIR panel button, repair cursor mode, and left-click-on-damaged-friendly for builders. Also fixed `buildExistingUnit` checking `isBeingBuilt` against the builder's definition instead of the target's.
- [x] Patrol: `PatrolOrder` loops through waypoints (re-queued on arrival), engages enemies in primary-weapon range en route unless on hold fire; PATROL button + `cursorpatrol` sprite; a single click patrols between the point and the unit's position.
- [x] Capture: `CanCapture` now parsed from FBI; `CaptureOrder` works like repair but accumulates `captureProgress` on the target and swaps owner at `buildTime`, clearing its orders/targets; `UnitCapturedEvent` drops it from the old owner's selection. CAPTURE button + `cursorcapture`.
- [x] Resurrect, implemented 2026-09-06 (`TOTALA-EXE.md` §98). The corpse-to-unit mapping is a string operation rather than a table -- the feature's own name truncated at the first underscore -- so `armsolar_dead` and `armsolar_heap` both give `armsolar`. `(BuildTime * 0.3) / (WorkerTime/30)` ticks, the one job of the three that scales with the builder; the unit returns complete, facing the way its corpse lay, on one hit point. Draws the nanolathe while it works. Still mod-only: no shipped FBI names `CanResurrect`. One departure in §88 -- the corpse is removed before the unit is placed, because a corpse is `blocking` and RWE refuses an occupied footprint.
- [x] **Capture progress goes with the captor** (2026-09-05, `TOTALA-EXE.md` §96). Asked for as a decay; the original has nothing to decay, because capture progress was never on the thing being captured. The Capture mission counts up in its own order record (`mission+0x36`, total in `+0x3A`) and the target unit has no capture field at all — so cancelling the order frees the count with it, re-ordering starts from zero, and two captors on one target race rather than pool. RWE's `CaptureOrder` now carries the pair the same way and `UnitState::captureProgress` is gone from the struct, the hash, the save and the dump. The clock came with it: `trunc(E*0.015 + M*3/14 + 150)` ticks, capped at 1800, scaled by `(hp+max)/(2*max)` and by `kills/5 + 10` tenths — so a damaged unit changes hands faster, a veteran one slower, and **the captor's `workertime` is not in it anywhere**: capture is one tick of work a tick for everybody. A nanoframe cannot be captured ("That unit is a cloud of vapor"), which RWE was allowing. `src/rwe/sim/capture.test.cpp`.
- [x] Transports (load/unload, `TransportCapacity`, `TransportSize`): first version landed 2026-08-28, see play-test round 2 below.
- [x] Self-destruct: `Ctrl‑D` starts a 5 s countdown (toggle again cancels), the sim detonates the unit with its `SelfDestructAs` weapon (new FBI field, falls back to `ExplodeAs`), no wreck; seconds remaining drawn above the unit. Blink/flash effect not yet done. The blink is fork issue #29.
- [x] COB getters: Health, VeteranLevel, MinId/MaxId/MyId, UnitTeam, UnitBuildPercentLeft, UnitAllied etc. were implemented in the merged `feats/next` work. Remaining FIXMEs (UnitTeam returning player id, UnitAllied = same owner) need a team/alliance model — tracked under multiplayer.
- [x] Pathing: units slow when climbing (top speed → ½ at the slope limit, floor ¼) (#45); ground steeper than half the slope limit is rough terrain for routing (#33); no diagonal squeeze between touching obstacle corners (#30); an unreachable move target ends at the closest reachable point and the order completes instead of re-pathing forever (#28). Tests in `src/rwe/pathfinding/pathing.test.cpp`.
- [x] Units rock when they fire (#40): `RockUnit(x, z)` is now called on every shot with the recoil direction in the unit's frame (Spring-style scaling).
- [x] Aiming scripts run twice (#42) (2026-09-15, §11 *One aim per shot*). Worse than twice: a commander attacking the ground ran `AimPrimary` 151 times for 12 shots, because a successful aim that found the reload unfinished went back to idle, and idle aims again — every other tick of every reload. The original raises bit 0 of the slot's flag byte when it starts an aim and starts no other while it is up (`0x49E211`), does not look at the slot at all while the reload counter runs (`0x49E3AE`), and lowers the bit only when the round is spawned (`0x49D78B`), when the drift check fails (`0x49D68A`) or when the target is lost. RWE holds the aim as `AimedInfo` now. The drift check this item was worried about is kept and runs when the reload does, so a target that has moved is still aimed at a second time. An aim that answers no is still asked again next tick where the original would wait (§91). `sim/aimpershot.test.cpp`, with the shipped ARMCOMLASER. Fork issue #18.

**In-game UI** (stated focus when upstream stalled)
- [x] F2 in-game menu: save/load, options, exit (#154). The panel and its options pages landed 2026-09-02; the flow around it was finished 2026-09-09 — see "The in-game menu is finished" below.
- [x] Hotkey help overlay (#155): F1 toggles a two-column reference of every binding.
- [x] **The unit info panel says what the original's says** (2026-09-05, `TOTALA-EXE.md` §99). `0x46A860` decoded end to end. The subject is the unit *under the cursor* and never the selection. Metal prints at one decimal place and energy at none, because the format strings are `"+%.1f"`/`"-%.1f"` against `"+%.0f"`/`"-%.0f"`, and all four are clamped at zero before formatting. Kills appear under the damage bar — no rectangle of their own; the routine takes DAMAGEBAR's left edge and its bottom plus two — as `1 kill` / `3 kills`, gaining `- Veteran` from the fifth, which is the whole of TA's veterancy display. The mission line is not composed anywhere: every mission record carries a display name at its `+0x00` and `0x439DF0` fetches the one for the current mission, so RWE transcribes both tables (`Standby`, `Moving`, `Nanolathing`, `Under construction`, `Annihilating`, …) and joins its orders to them. And the second name-and-bar slot shows **whatever the current order points at** with its health — a builder's nanoframe, a guard's charge — which is where the build progress the entry asked for lives. §29's "the stockpile progress is shown nowhere" was wrong: it read to `0x46B400` and the bar is at `0x46B445`, captioned `Weapon`, so RWE's silo readout is a restoration after all and only its caption was invented. `src/rwe/game/infopanel.test.cpp`.
- [x] Build menu paging, queue display, `Shift` queue count badge — paging (the ARMPREV/ARMNEXT gadgets and the `,`/`.` keys), the `+N` badge and Shift-for-five were already in; what was missing is that the badge went stale as a factory worked through its queue, because it was only refreshed off a command and nothing passes through the UI when a unit *starts*. The original does not try to be clever either: `0x4199B0` rebuilds the caption of every gadget on the page on every refresh, counting the outstanding orders on demand through `0x439D80`. RWE now does the same once a frame.
- [x] Pause/speed indicators on screen — already present in the merged work ("Paused" and the +N speed readout).
- [x] Resource stall: spending is now gated on what is actually on hand at the moment (stock + income so far this second − spent so far), so an empty stockpile throttles building continuously to the income rate instead of one-second bursts; stalled energy/metal bars flash red as in TA.
- [x] **Focused-control highlight (#5) and list-box selected-item brightness (#6)** (2026-09-05, §99). Both turned out to be one read of the gadget renderer. The only comparison against the panel's focused-gadget index anywhere in it is in the text-box draw, which puts a one-pixel vertical caret at the end of the text in interface colour 9 (light blue) — buttons and list boxes show no focus at all, so the caret *is* the highlight. RWE drew an underscore whether the box had the focus or not, and `UiPanel::focus()`/`unfocus()` had their tests inverted, dereferencing an empty optional. The selected list row is brightened by running its rectangle through `PALETTE.LHT` at level 30 — measured at a median 1.84x on luminance, applied after the text so the text brightens too — where RWE washed it with 12% white and you could barely see it. The same call greys a control at `PALETTE.SHD` level −20 (0.82x). **The three gadget-renderer details §99 left owing are all in as of 2026-09-10** (§19, §99). *Greying* had in fact landed on 2026-09-02 and both documents were stale on it: a disabled `UiStagedButton` draws the greyed frame the artists put one past the pressed frame in the button's own GAF, rather than running the rectangle through SHADE row 12 — the two agree because the artwork was drawn to agree, not because the code does the same sum, and only a mod whose GAF carries no such frame can tell them apart. *The caption drop shadow*: only for a gadget whose attribs carry bit 3, which `0x4A59A4` tests and the first port missed; the shipped menu buttons do not set it, so they have none (corrected 2026-09-11 after a play-test against the original, `2fc621c0`). *The quick-key underline*: where the gadget's `quickkey` character appears in its caption, a one-pixel line goes under it in interface colour 2, GUIPAL green, (0, 128, 0) on screen, not in the caption's colour, one row below the height of the font's `I`, its offset and width measured in the font's own per-glyph advances by `findCharacterInText`. That match is case-insensitive and has to be — RWE has folded the gui file's key to an SDL keycode by the time a button holds it — which is also the better reading: four shipped gadgets are authored in the other case (MISSION.GUI's `SELECT` against `Select Mission`, and the three `UNDO` buttons against `Undo Changes`) and would lose their underline to an exact test. The same pass wired the main menu's Credits button to `5.zrb`; see the movies below. `src/rwe/UiRenderService.test.cpp`.

**Game flow**
- [x] **The end-of-game screen, as the original draws it** (2026-09-15, §104). The placeholder result box is gone. A decided game now plays the original's sequence: `igvictory` or `igdefeat` over the frozen battlefield with two beeps, the ten-step fade to black `0x41FA8F` spends a tick at a time, and then the chart on `bitmaps/OUTCOME0.PCX` — the artwork's own frame, button surround and eight column headings — with a row per player and seven bars that run up left to right, one column starting every ten ticks and each bar full after fifteen frames. Kills, Losses, Energy Produced, Metal Produced, Excess Energy, Excess Metal, Score, measured against the largest figure anyone reached with the original's floors of ten and a hundred under them; a click fills every bar at once, as it does in the original. The score is `kills * killmul + seconds * timemul` read out of the **map's** OTA, each term truncated separately and the total floored at zero. The title is `victory`/`defeat` out of `ENDMSN.GAF` and the Main Menu button is ENDMSN.GUI's own, wearing the BUTTONS0 face; everything is set in Haettenschweiler, the face the headings baked into the bitmap were drawn in. The four economy columns needed new sim state — `metalProduced`, `energyProduced`, `metalExcess`, `energyExcess` on `GamePlayerInfo`, counted where the original counts them: income as it arrives, and excess as the storage cap throws it away. `RWE_DEBUG_ENDGAME=<seconds>[L]` forces the sequence without playing a game out. `EndGameStats.test.cpp`, `economy.test.cpp`. Not decoded: which of the six shipped beeps the original plays — nothing in the executable, SOUND.TDF or any gui file names one, so RWE uses BEEP6.
- [x] **An anti-air unit comes off a ground target when an aircraft arrives** (2026-09-15). Reported from a play-test: a Jethro shooting at tanks. A bad target category is a preference when a weapon *picks* (§ target selection, `0x40BA4D`), which RWE had, but it is more than that once a target is held: the scan at `0x4089A0` keeps an existing target only while it is alive, in range and **not** in that slot's bad-target set, and drops it where it stands otherwise so the chooser runs again. RWE never re-chose, so the first thing an anti-air unit shot at was the last. The drop is phased per unit to the scan's own cadence of about once a second rather than run every tick, and an explicit attack order is left alone. `targeting.test.cpp`.
- [x] End-of-game flow: result panel instead of exiting; **superseded by the entry above** — the placeholder panel it describes (VICTORY/DEFEAT/DRAW, game time, units destroyed/lost) has been replaced by the original's own screen. What still holds: the sim keeps running for spectating; Escape returns to the main menu. Single-player games are never "decided". Per-player kill/loss tallies added to `GamePlayerInfo`.
- [x] Line of sight / fog of war / radar: per-player explored/visible/radar grids in the sim (32 world units per cell, rebuilt each tick); sight rays are blocked by higher ground so hills cast shadows; unseen enemies hidden, radar contacts drawn as blips, unexplored features hidden, terrain and minimap fogged with a soft ragged edge (4× upsampled noise threshold, linear filtering), unseen units not clickable; F10 toggle. Radar jammers, sonar, stealth and cloak followed later in Phase 1 and are all in.
- [x] Construction effects like TA: nanoframes keep their cast shadow but the model's own silhouette is punched out of it (stencil cut-out); a wireframe of only the camera-facing, unoccluded polygon edges (depth-tested, ground-contact edges skipped) blends slowly green→white→black; the nano line is replaced by a dense spray of small square particles (TA greens, lighter ones favoured) from the builder's nano piece that fans out to the target's footprint, reversed for reclaim, interpolated per frame. Fog edge is a crisp stepped contour at 8-unit texels like TA's, rebuilt only when the grid changes. PAUSED uses TA's own `anims/IGTITLES.GAF` title (igvictory/igdefeat loaded too).
- [x] Fog of war drawn as in TA: the terrain shader greys remembered ground (luminance × 0.7) and blacks out the unknown, sampling the per-cell fog map at a world-space-jittered position so the 32-unit boundary is eroded by a few pixels of fixed noise (measured from the original: 32-px grid, radius = SightDistance, ±3 px ragged edge). Sprite features in fog are greyed too.

The feature's `seqnameburn` loops while alight. Tests in `burning.test.cpp`.

- [x] **How the original orders what it draws** (disassembled from `TotalA.exe`, 2026-08-31). There is no depth buffer at the world level at all: TA is a pure 8-bit software painter and everything — terrain, units, features, shadows, particles — goes through the same three blit routines in call order, last one wins. The world render function is `0x468cf0`. Objects are bucketed by **world Z alone, quantised to 16 units** (`0x4697ed`), ignoring height entirely even though the projection is `screenY = z − y/2`; within a bucket there is no secondary sort. (`sortbias` is parsed from the FBI into `unitdef+0x21a` but read nowhere — dead in this build.) Particles are not in that list at all: they live in a separate manager with **ten hard-coded layer buckets**, and each SFX type is hand-placed in one — wakes on 2, weapon impacts on 6, **VTOL and thrust exhaust on 7**, damage smoke on 9 (over everything, including health bars). So particles are not uniformly in front or behind; each effect is placed by hand.
  **Why the Atlas exhaust sits under the aircraft in the original**: explicit layering, not depth and not the spawn position. Layer 7 is drawn at `0x469b38`, and the very next pass at `0x469b3d` draws every object whose `occupy != GROUND` — airborne units get their own late pass, so the aircraft is blitted over its own exhaust a few instructions later. Had it been on the ground the exhaust would have landed on top of it. RWE reaches the same result by a different route (depth testing against world Y, which is what its camera uses for depth); the two agree for an airborne aircraft, and differ only in that RWE will also let a tall ground unit in front occlude the plume, which TA would not. Judged the better behaviour for a renderer that has a real depth buffer, so kept.
- [x] **How the original does fog of war, and how terrain affects it** (disassembled from `TotalA.exe`, 2026-08-31). The grid is **32 world units per cell**, two heightmap samples across — which RWE already matches. Three states come from two arrays: one global *explored* array of `uint16` used as a bitmask, one bit per LOS group, set-only; and a per-player *visible* array of one byte per cell used as a **reference count** of how many of that player's units see it. `UpdateUnitLOS` (`0x4827b0`) runs per unit per tick but is **incremental** — it early-outs unless the unit changed cell (or, in terrain mode, moved its eye by more than 5), then subtracts the old stamp and adds the new one.
  Sight comes from FBI `SightDistance` (`unitdef+0x202`). There are three modes, exposed in the skirmish GUI as **Permanent / True / Circular**, defaulting to **True**. Circular mode does not ray-trace at all: it blits a hand-drawn mask sprite from `anims/vismasks.gaf`, ten frames of radius 5 to 14 cells, so sight is `clamp(SightDistance/32, 5, 14)` cells and saturates at 448 world units. True mode walks a **fixed fan of authored rays read from `gamedata/los.tdf`** (`TABLE1`..`TABLE9`, each a list of stepped `dx,dy` runs replicated into four quadrants) with a running maximum-slope horizon — shadow casting, not a per-cell retrace — and its radius is capped at **8 cells, 256 units**, because the table index is `min(sight/32, numtables-1)` with `numtables=9`.
  Terrain occlusion uses its own grid holding **two heights per cell**: `max(seaLevel, (2·max+min)/3)` decides whether a cell is *revealed* and `max(seaLevel, (max+2·min)/3)` decides whether it *occludes*, so it deliberately errs toward revealing. The eye is `clamp(unit Y, ≥ seaLevel+1) + the model's own height` (the maximum vertex Y of its 3DO, not an FBI field). The horizon is only raised on cells the ray actually revealed, so once a ray is blocked the horizon stops rising. Water is flat ground at its surface.
  **Radar has no grid at all** — it is a per-tick unit-versus-unit range query with `range = RadarDistance + 2 × altitude`, terrain never blocks it, and it flags units rather than revealing ground.
  Drawing is **marching squares over cell corners**, not per-cell blocks: an overlay grid records which of the four surrounding cells are dark, and each 32×32 screen tile picks one of 14 authored frames from `anims/fog.gaf` (`Black1..4` and `Gray1..4`, 14 frames each), with the variant chosen as `(cellX + cellY + scroll) & 3` so the ragged edge is fixed in world space and does not shimmer when scrolling. Fully-unexplored tiles are a solid palette fill. The ragged boundary is in the artwork, not in a shader.
- [x] **Fog of war rebuilt to match the original** (2026-08-31). The original picks in `0x40B7B0`: it scores every candidate `rand(dx² + dz²)` and takes the **lowest**, so the nearest usually wins but not always, which is the whole of TA's spread of fire. A weapon's `wpri_/wsec_/wspe_badTargetCategory` does **not** veto a candidate, it holds it back as a fallback — so a Samson with no aircraft about still shoots at tanks. `ShootMe` (absent on exactly the fifty-four passive buildings) keeps units from opening fire on an enemy solar collector unless the shooting player is a computer, `toAirWeapon` refuses a ground target outright, and `NoChaseCategory` governs only whether a unit leaves its post — RWE applies it to the search that breaks a patrol off. Categories turned out not to be ids on the unit at all: each category name owns a 512-bit set of *unit type indices*, and `unit+0xA6` is that type index. **Return Fire** was a second name for hold fire; in the original it lives in the damage path (`0x489CE0` → `0x406F80`) and the only difference from fire at will is that the retaliation test accepts firing mode 1 or 2 while the hunting scan demands 2. Switching to hold fire or return fire also drops the weapon's current target, as the original's `Standing_FireOrder` handler does. Written up in `TOTALA-EXE.md` §9; `targeting.test.cpp` covers all of it.

- [x] **Missiles have a motor** (disassembled from `TotalA.exe`, 2026-08-31). Every projectile flew at a constant `weaponVelocity` and `weaponacceleration` / `startvelocity` / `selfprop` / `twophase` / `vlaunch` / `flighttime` were all dead, so a Rocko's rocket left the rail at 21.67 a tick instead of 15, and a nuke silo fired its missile out sideways through its own building. The original's model is one motor and one steering law (`0x49B720`): `startvelocity` is the launch speed, `weaponacceleration` is added every tick, `weaponvelocity` is a **cap** and never a cruise speed, and the burn lasts `range / weaponvelocity` ticks unless `noautorange` is set, in which case it is `weapontimer`. Running out is not death — without `burnblow` the missile keeps its velocity and coasts under gravity, which is why one fired at the far edge of its range arrives unguided and why misses arc into the ground. Steering is gated on **`guidance`, not `tracks`**, and turns the missile's own heading and pitch, each by at most `turnrate/30` per tick (the TDF number is per second; RWE was applying it raw, thirty times too fast, which snapped every tracking missile straight at its target). `vlaunch` leaves the tube at pitch `0x4000` with **zero velocity**, so the whole climb comes out of the motor, and `twophase` flies that climb blind and then resets the burn to `flighttime` and turns over. `flighttime` is at `wdef+0xFC`, not `+0xFA` — that slot is `smokedelay`, and the parser's stores land one key late. Replayed standalone against the shipped TDFs before anything was written: a Diplomat's rocket climbs 503 units over 150 ticks, peaks at 596 and lands 11 units from a target 800 away; RWE now measures 503, 589 and 1.0. The `/900` on `weaponacceleration` is pinned by the nuke, which climbs 637 and peaks just under its own hardcoded 700 cruise altitude — at `/30` it would climb 1750 and have to dive.
- [x] **A damaged unit's smoke puffs stop where the original's stop** (disassembled from `TotalA.exe`, 2026-09-01). The roadmap had this down as an effect RWE was missing entirely; it was not. Nothing in the engine decides when a unit smokes — every call site of every smoke spawner in the particle manager is accounted for, and none of them is a unit update. The trigger is the `SmokeUnit` thread in each unit's own COB, word for word the same in 186 of the 200 scripts in `rev31`: it smokes below **66%** health, sleeps `max(health% × 50, 200)` milliseconds between puffs, and rolls `Rand(1, 66)` for white against black on every one, so a lightly hurt unit is nearly all white and a dying one nearly all black. RWE already ran that script and already spawned the puffs. What was wrong was the puff: RWE played all twelve frames of `smoke 1` at an even two ticks each, so every puff swelled to full size and they all looked alike. The original holds the first frame for the emitter's own **seven** ticks, rerolls **three to five** for each one after (`0x4753A8`), and picks the frame to stop on when the puff is born as `2 + rand·(frameCount − 3)/0x8000` (`0x474F21`), so a puff shows between two and ten frames, most die small, and the last frame of a sequence is never reached. One `emit-sfx` is exactly one puff — the emitter's lifetime argument is zero, so the single emit inside `Init` is all of it. Written up in `TOTALA-EXE.md` §4, which also corrects that section's claim of an off-by-one in the FX.GAF loader: the slot map is direct, the store just sits between the next call's argument pushes. Not ported: the wind drift (`windXZ × 8` a tick -- RWE keeps a map wind vector now, so this wants only the particle code wired to it, not anything decoded), and the explosion and burning-wreck plumes that run off the same class.

- [x] **Shading, the exact table** (2026-09-08). The row was already the original's; what a row *meant* was a curve. `PALETTE.SHD` stores palette INDICES from a nearest-neighbour search, so a row does not scale a colour -- it snaps the scaled colour back onto the 256 entries that exist. A census of the shipped table says how far that is from a multiplier: at row 31 it leaves **eight** of the 256 entries exactly where they were and puts **fifty-eight** of them on white, where the fitted curve claimed a uniform 1.807x for every one of them, and row 15 is the identity for 232 of them. The texel's own palette index now rides through the texture atlas in a second single-channel copy, and the fragment reads `SHD[row * 256 + texel]` out of a 256x32 image of the table -- the original's inner loop entire (`0x4C81A4`-`0x4C81BD`): one shift, one add, one byte load, no second mask, no clamp, no blend between rows. Flat-coloured polygons come with it, since the original's own flat filler at `0x4C0B10` indexes the same table with the polygon's colour index standing in for a texel.
  Two things were measured before any of it was written, and one of them killed the obvious implementation. **The generator is exact**: `0x4BADF0` transcribed into C++ reproduces the shipped `palettes/PALETTE.SHD` byte for byte from `PALETTE.PAL` -- 0 of 8192 bytes differ -- so a data set missing the file has the table rebuilt from its palette rather than falling back to a curve, and that transcription is what `src/rwe/ShadeTable.cpp` ships. And **the cheap version does not work**: expressing the lookup as a per-texel ratio applied to the mipmapped colour, which would have kept the atlas's own filtering for nothing, loses the value on 431 of 24576 channels with a worst case of 119/255 across 38 palette entries -- a channel that is zero before the row cannot be scaled into one that is not. So the colour is read from the table and the atlas's filtering has to come with it: the index atlas carries a mip chain built by plurality vote, because GL's box filter would average indices and the mean of two palette indices names a third colour that is nowhere between them. `src/rwe/ShadeTable.test.cpp` pins the reader, the generator against an exhaustive nearest match, and the image.

- [x] **Eight hundred units at 36fps, up from eight** (2026-09-04). Both halves of the cost were found by measuring, and the guess would have been wrong — the renderer was never the problem. - [x] **Wind on ballistic rounds** (2026-09-17, §7). The original adds the map's wind vector to every ballistic and dropped projectile's **position** every tick, on top of gravity (`0x49BD10`), and RWE did not have it at all -- there was no map wind anywhere in the simulation, because `updateWind` drew a speed and a direction, spent them on the generator output and threw both away. The simulation keeps a `currentWindVector` now, rebuilt only when the wind changes, and `updateProjectiles` adds it in the ballistic and bomb branches. **The findings document had the vector's two components the wrong way round, and porting it corrected them:** §7 said X was `−2·cos(dir)·speed` and Z `−2·sin(dir)·speed`. X comes from `0x4b70ef` and Z from `0x4b7123`, the two routines identical but for an index the second advances by `0x4000` -- a quarter turn -- and both read the table at `0x509f00`, whose first entry is `0` and which peaks at `0x2000`. That makes it a **sine** table of amplitude 8192, so the first routine is sin and the second cos, not the reverse. (Each multiplies by the speed and then shifts right by 13, which exactly cancels the 8192, so a routine returns `trig(dir)·speed`.) The error was invisible in play -- against a uniformly random direction the two conventions give the same distribution -- which is why it survived the first reading and why the test pins fixed cardinal directions instead of sampling. The components are 16.16 like a position, so Brain Coral's `maxwindspeed` of 3000 is 0.092 world units a tick: roughly six units over a Crusader shell's flight against a damage radius of 24, a real nudge rather than a dominant force. That figure is also what pins the `/65536` -- without it a shell would move 6000 units on its first tick and leave the map. Nothing compensates for the drift: the original's own bombsight does not model the wind either, so a bomber's aim is now very slightly downwind and `predictBombImpactPoint` matches it by ignoring the wind too. This is new state on the simulation, so it is threaded through `save_util`, `GameHash_util` and `dump_util` per the determinism rule, and hashing it costs nothing on disk because no replay or save stores a `GameHash`. `sim/wind.test.cpp` covers the formula at fixed directions, the strictly horizontal Y the binary never writes (`globals+0x37ED0` is never written anywhere), the becalmed map, the `updateWind` wiring, and -- with a line-of-sight round as the control -- that the two branches which should feel the wind do and the one that should not does not. **The smoke drift** off the same two words scaled by 8 a tick (§4) followed on 2026-09-24 (#111): the particle update takes the vector times eight and every puff of smoke opts in.

It was one in two ways. - [x] Drop handling instead of hard failure. Rejoining is still owed and is
      issue #44's third part. A lost peer used to freeze the game for
      everybody with nothing on screen and a line a frame in the log, because
      a lockstep tick cannot run without every player's commands for it. Now
      the pause banner comes up naming who is being waited for and counting
      down, and after `drop-timeout` seconds (rwe.cfg, 10 by default, 0 to
      wait for ever) the rest carry on without them. Their units stay exactly
      as they were, with the orders and the fire mode they had, which is what
      the original does.

      **The drop is a command, and it is applied when it arrives rather than
      when it is popped.** That is the one departure from how every other
      command works, and it is forced: what the drop unblocks is the pop
      itself, so a drop waiting its turn would wait for ever. It is safe
      because the command says a *tick* and not a moment -- `fromTick`, the
      first tick the lost peer's commands are taken as empty -- so applying it
      early, late or twice all come to the same thing. Peers can hold
      different amounts of a lost peer's stream, a packet having reached one
      and not another, so the cut forces both ends: what is past it is
      discarded, what is missing below it is filled in.

      **Exactly one peer may issue it**, or two drops naming two ticks would
      cut the stream in two places. Which one is computed rather than agreed,
      from state every peer already shares: the lowest-numbered peer that is
      neither the player in question nor itself dropped. That is the host in
      the ordinary case, and the point of the rest of it is that the host
      going is the likeliest failure of all and somebody has to be able to say
      so. Measured on loopback, off-screen: killing the non-host, killing the
      host, and three peers with one killed -- in which the two survivors cut
      at the same tick and agreed on all 1,536 ticks compared, with the sync
      hash check live throughout. Not handled: two peers lost at once, which
      would leave two deciders.
- [x] **A dropped player can come back (#188, the third part of #44).** The
      inverse of the drop, and the same shape: the stream reopens at an agreed
      tick, and from that tick the game needs that player's commands again, so
      every peer stalls there until they arrive. That stall is the design. It
      makes a rejoin a lockstep event agreed by every peer at one named tick
      rather than a race between a catch-up and a running game, and the waiting
      caption the drop half added is already the thing that shows it.

      **One number, not two.** The recording handed over runs through the tick
      before the rejoin and no further, so both streams in both directions
      resume at that one place and there is no gap to bridge. The command
      stream's sequence numbers are absolute positions, so saying "resume at
      R-1" is the whole of it; the sync hash stream is numbered the same way
      but counted rather than carried, so a returning peer re-registers as a
      hash source from its own first tick and is left out of the comparison
      below that rather than waited for.

      **The catch-up is the replay viewer's path**, deliberately. Winding a
      recording forward already takes every player's commands from the file,
      feeds no computer player, and neither computes nor sends a sync hash --
      four of the five things a catch-up wants, none of them written twice.
      740 ticks wind in about 2.5 seconds.

      **Five things went wrong between "it loads" and "it plays", and each is
      a rule.** Deferring the network thread deadlocks the scene, which asks it
      for the round trip time every frame; a returning peer listens from the
      start and withholds what it hands the simulation instead. A recording
      supplies a set per player per tick unconditionally, and a rejoin has
      already filled in the ticks below it -- so a peer winding across its own
      rejoin arrived a hundred sets deep in its own buffer and submitted
      nothing live. That predicate is absolute, so a viewer seeking backwards
      has to move the streams with the scene time, which also fixed a viewer
      wound back past a drop still treating that player as gone. Every hash
      source on a rejoining peer starts at the rejoin tick while the comparison
      counter starts at 1, so it compared nothing at all until it was moved up
      to meet them. And the viewer's end-of-recording pause caught the
      catch-up, the check that releases it having lived in a tick that a paused
      playback no longer dispatches.

      **The lobby carries the bytes**, which was the maintainer's direction:
      the engine speaks to its own launcher over `--bridge` (one JSON object a
      line, in on stdin and out on stdout, the dialect `rwe_bridge` already
      speaks), and five lobby messages do the rest. Who may answer a rejoin is
      computed rather than agreed -- the lowest-numbered slot still in the
      game, the engine's own rule over facts the server already has. Every peer
      of a lobby game records a replay now, because the recording is the only
      thing that keeps the commands.

      **Measured on loopback, off-screen**: killed peer restarted and rejoined,
      the two agreeing on all 1,975 ticks compared; the same driven over the
      bridge rather than the test hook, agreeing on 1,842; and with a
      counterfeit desync after the rejoin, the returning peer names the right
      tick and writes its dump, which is the hash check being live on a peer
      that was not there for the first half. The host's own recording of such a
      game, replayed headlessly, reproduces its hashes exactly across the drop.
      Not run against two live launchers and a server, which wants two
      machines.

      agreeing there. The solar collector is what showed it -- trapezoid panels
      under a strongly striped texture, kinked along the diagonal.
      **Shadows on water** were decoded and declined, which is written up at
      the end of `TOTALA-EXE-RENDER.md` §100: a building's projection is drawn
      flat at the ground under it wherever that ground is, a finished unit's
      copy is not cut at the water line, and the only water test in either
      pass is the one on map features in §3. Nothing here departs from the
      original, so it is not in §88 or `compatibility.md` either. It went the
      other way in the code, in fact: a floating building's shadow used to be
      lifted to the surface with `rweMax(groundHeight, seaLevel)` and now sits
      on the sea bed where the projected pass puts it.
      **The animation off-by-one** is `GameScene::renderTime`. Everything that
      moves is drawn as `lerp(previous, current, interpolationFraction)`, so a
      frame shows the world between the end of tick `gameTime - 1` and the end
      of `gameTime` -- and a GAF animation keyed on `gameTime` ran a whole tick
      ahead of the units it belonged to. Feature burn loops, sprite and wake
      and nano particles, projectile sprites, muzzle flashes, the build-cycle
      colours and the order-line march all take the render clock now, and so do
      the two passes that *remove* finished effects, because a flash dropped a
      tick early is a flash whose last frame is never drawn. The fraction is
      deliberately not in the answer: every one of these steps on whole ticks,
      and `floor((t - 1 + frac) / period)` is `(t - 1) / period` for any
      fraction below one. A clock the player reads and a countdown are not
      animations and still ask the simulation. `game/animationclock.test.cpp`.
- [ ] Run the engine against Core Contingency, Battle Tactics and the big
      community mods, and log incompatibilities as issues. **Less blocked than
      this line used to imply** (checked 2026-09-23): the engine's own data
      directory on this machine carries `ccdata.ccx`, `ccmaps.ccx`,
      `ccmiss.ccx`, `btdata.ccx` and `btmaps.ccx` beside the base game and
      nine community `.ufo` packs, and `.ccx` is in the VFS's extension list
      (`CompositeVirtualFileSystem.cpp`), so every arena run and every
      play-test in this repo has been loading Core Contingency and Battle

      pass -- play their units and their maps on purpose and write down what
      breaks -- and the fact that nothing has fallen over by accident is worth
      something but is not that pass. TA:Escalation and TA:Mayhem are the part
      that really is not here.
- [x] Invalid UTF‑8 resilience (#14, 2026-09-23). `ensureUtf8` in
      `util/rwe_string.h` is the boundary: valid input comes back byte for
      byte, anything else is read as latin1. latin1 because it is the fallback
      that loses nothing -- byte 0xE9 becomes U+00E9, so the original byte can
      still be read differently later -- and because it is what the TDF parser
      has always done for TA's own files, which are latin1 where they are not
      ASCII. It is applied where text enters the interface rather than where
      it is drawn, drawing happening every frame and setting happening once:
      `UiLabel::setText`, `UiListBox::appendItem` (the map names, which are
      file names out of an archive and so bytes somebody else chose) and
      `UiStagedButton::setLabel`, plus `parsePlayerInfoFromArg`, a name in a
      `--player` spec being the shortest way to reproduce the crash.
      Two faults fell out of writing the test for it, both invisible while
      every string in play was ASCII. `utf8Split` built each piece by handing
      a pair of `utf8::iterator`s to `std::string`, which narrows every code
      point back through `char`: a name given as perfectly good UTF-8 came out
      of the split as latin1 again, and the arena's `run.json` threw on it and
      was left empty. And the trims passed a code point to `isspace`, which is
      undefined for a value that does not fit an unsigned char.
- [x] `docs/compatibility.md` (2026-09-23): what TA behaviour is intentionally
      not replicated, and what of it is kept although it looks like a defect.
      The plain-language face of `TOTALA-EXE.md` §88, grouped by *why* rather
      than by subsystem, because the reason is the part that stops an entry

      has to stay deterministic, there is no palette to do the trick with, or
      it was measured and the original's answer played worse. It opens with
      the other list -- the quirks reproduced on purpose, from the purple halo

## Phase 5 — Performance, renderer, platform (ongoing, low priority until Phase 1 done)

The simulation half of this phase was brought forward and largely done — see "Eight hundred units at 36fps" in Phase 1, and `battle_test` and `RWE_ENABLE_SIMPROF` for how to measure the next round. What follows is what is still open.

- [x] Renderer profiled and cut, 2026-09-05. `RWE_ENABLE_RENDERPROF` (`src/rwe/render/render_prof.h`, the same shape as `RWE_ENABLE_SIMPROF` and off by default) breaks the frame down by phase; `battle_test` at 400 a side on Coast To Coast, Release, 1280x800, is what it was measured on. **The 23 ms claim did not survive contact with the profiler.** At 800 ground units the renderer was 29.8 ms a frame and the simulation tick 4.2 ms — the sim work had taken the tick from 25 ms to 4, so the renderer was not merely the largest cost but nearly the whole of it. At 800 *hover* units the largest cost was neither: 130,000 live wake dots cost 10 ms a tick in `updateParticles` and 12.9 ms a frame to draw. What the breakdown named, and what came of it:
  - Piece transforms were looked up by name — a `toUpper()` allocation and a hash lookup per link of the parent chain, per piece, per unit, per frame, and again for the shadow pass. `GameMediaDatabase::getUnitModelRenderInfo` resolves a model's hierarchy, meshes and rest transforms once. 17.7 ms → 5.0 ms.
  - Nothing was culled. `ViewCullTest` drops units, mesh features and their shadows whose model cannot reach the view (orthographic projection, so the test is a transform and four comparisons). 10,400 piece draws → 2,750.
  - Wake dots were all built and uploaded, on screen or not: 770,000 vertices, 18 MB a frame. Culled at the point they become geometry, and the batch's storage kept between frames. 12.9 ms → 4.0 ms, and per vertex 23.5 ns → 15.1 ns.
  - `updateParticles` asked `MapTerrain::getHeightAt` — a vertical ray cast against up to sixteen heightmap triangles — whether each wake dot had reached the shore. Every height that query can return lies between the lowest and highest corner of the cells it looks at, so a dot over water is settled by sixteen byte comparisons and the ray is only cast near a shore. 10 ms a tick → 3.6 ms.
  - Net: 800 ground units 34.0 ms → 16.7 ms a frame (29 → 60 fps, now on the 60 Hz vsync cap, with the world render itself down from 28.1 ms to 5.1 ms); 800 hover units 84.9 ms → 26.4 ms (11 → 38 fps).
- [ ] What the profiler names next, at 800 hover units on a 26 ms frame: the wake batch at 4.0 ms (still 260,000 vertices a frame — a persistent VBO instead of a fresh one, or point sprites, is the next step), the stencil shadow pass at 3.0 ms, `MapTerrain::getHeightAt` itself (the ray cast is the wrong algorithm for a height sample, but it is sim code and a desync risk, so it wants its own pass), and the muzzle-flash pass at 1.6 ms, which is not culled at all. Batching unit meshes by texture (#16) is still not done and is worth doing once something other than draw-call count is the limit — at 2,750 piece draws the unit pass measures 0.17 ms, so it is not the limit today.
- [x] Raise the pathfinding budget past four searches a tick (see Phase 1) once a play-test says what it does to how units behave. (2026-09-10: the play-test was done and it stays at four; reopen only if a melee jams)
- [ ] TDF parser speed in MSVC Debug (#66) — Kevin's `optimize-tdfparse` was merged; re-measure.
- [ ] SDL_gpu backend (from `experimental/sdl-gpu`) once the GL renderer is feature-complete; this is the path to Vulkan/Metal/D3D12 and to WebAssembly (#178's motivation).
- [ ] Protobuf upgrade (from `update-protobuf` branch) with a CMake build; or replace protobuf with a hand-rolled binary codec — the schema is ~15 messages.
- [ ] Official Linux (AppImage — job exists) and macOS builds; reproducible builds (#35).
- [x] **`GameScene.cpp` is split, and then `GameScene_commands.cpp` too** (2026-09-06, again 2026-09-09). Not for readability in the end but because the translation unit had outgrown what a COFF object can describe: 11,466 template instantiations, 46,124 sections against a signed-16-bit ceiling of 32,767, and the assembler switching the object to `pe-bigobj` without a word. The MinGW64 CI runner's binutils could not read that format back and dropped every COMDAT definition while keeping the references — a Debug-only link failure, 1,124 undefined symbols out of one object, every one a template or a lambda, while Release passed because the optimiser folded them away. Two more cuts followed on 2026-09-09, both of code that is dense in the way that costs sections rather than merely long. `GameScene_debug.cpp` took the parts no game ever reaches — `battle_test`'s standing battle and the F10 panel's unit spawner and placer — and `GameScene.cpp` went from 18,267 sections to 15,644. `GameScene_menu.cpp` took the F2 panel and everything behind it: the Resume/Options/Restart/Exit flow, the confirmations, the PREFS composite and every control wired to it, and the save and load dialogs with their list; `_commands` went from 26,721 to 21,981, from 82% of the ceiling to 67%, and is still the largest. Eight files now, beside the older `_util`. **What the measurement says, and it is the reason to stop here rather than keep cutting:** the count is a budget rather than a free win, because the standard library's floor is paid once per translation unit — the menu cut added 8,365 sections in total to take 4,740 off the peak. Where a new file lands is decided mostly by its includes: `_debug` came out at 4,839 with a tight list, `_menu` at 13,105 because it genuinely needs `MainMenuScene.h`, `LoadingScene.h` and `SaveFile.h`.

## Release cadence

- Pre-release tag on every merged phase milestone; changelog generated from commit titles.
- **A rolling `nightly` pre-release of `revival`** (2026-09-24). Every push that builds green publishes or updates one pre-release under the lightweight `nightly` tag: the Windows MSVC zip and installer plus the Linux AppImage, the tag force-moved to the built commit and the body naming the full hash and the commits since the previous nightly. Stale assets are deleted first, because each build's filenames carry the commit (`git describe`) and so never collide on their own. The tag is lightweight on purpose — CMake's `git describe` reads only annotated tags, so `nightly` stays out of the version the binaries report. This is for playtesting the latest build without waiting for a version tag; real releases still come from `v*` tags through `release.yml`.
- **The commit hash is a build fact in its own right** (2026-09-24). CMake reads `git rev-parse HEAD` into `rwe::GitHash`, and it is written to the crash report (`commit:`), the desync dump (`commit`), the arena report (`gitHash`) and the startup log. `git describe` alone drops the hash whenever HEAD is exactly on a tag, which is every release build, so a bug report could otherwise name a version and no revision.
- Keep `CLAUDE.md` accurate — it is the onboarding doc for AI-assisted work on the codebase.
- Public announcement (TAUniverse thread t=45555, upstream issues) is deliberately deferred until the project is playable.

## Phase 7 — Quality-of-life mods, as demos (planned 2026-09-18)

None of these is in the original, so none of them belongs in the default game: the project's rule is that RWE plays as Total Annihilation does unless someone asks it not to. They are planned as **opt-in demos** of what the engine can carry beyond the original -- each behind its own switch, off by default, and each small enough to be read as an example of where such a thing hooks in. Anything that changes what a unit *does* (as opposed to what the interface offers) is simulation behaviour and has to be a game option every peer agrees on, saved with the game and part of the replay header, or it is a desync; interface-only ones are local settings and need none of that.

Checked against the code as it stands, so nobody builds what is already there:

- [ ] **Economy-structure attack.** Once the armed units in view are dead, units go on to the structures rather than standing among them. *Not present.* Target selection follows the original's eligibility and priority (`TOTALA-EXE.md`, target selection), which has no such fallback. Simulation behaviour: a game option, hashed and saved.
- [ ] **Factory repeat.** A toggle on a factory that puts each finished item back on the end of its queue. *Not present* -- a factory's queue is consumed as it builds. Simulation state on the factory (`UnitState`), so it needs the four places: the struct, `save_util`, `GameHash_util`, `dump_util`.
- [x] **Repair as the suggested action on a damaged structure.** *Already a feature, and the original's own:* with a builder selected, the cursor over a damaged allied unit is the repair cursor and a click issues the repair (`DefaultAction.cpp`, both mouse schemes; an unfinished frame gets the same cursor and a complete-build order instead). `TOTALA-EXE.md` §103. Nothing to build unless the wish is for something beyond the cursor -- a highlight on the damaged building itself, say -- in which case say so and it becomes its own entry.
- [ ] **Idle construction units: a display and a locator.** *Half present.* `Ctrl+B` already cycles through idle builders, selecting and centring each, which is the original's key. What is missing is anything on screen that says there ARE idle builders without being asked: a count on the HUD, and a click that does what `Ctrl+B` does. Interface only.
- [ ] **Box-select takes the fighters when the box is mostly fighters.** *Not present.* A drag box selects everything in it, as the original does. Nearest existing thing is `Ctrl+S`, armed units on screen. The rule wants pinning down before it is written -- "predominantly" as a share of units, or of metal? and do builders caught in an army's box drop out, or only buildings? Interface only.
- [ ] **Push an order to the FRONT of a queue, keeping the rest.** *Not present.* An order is issued one of two ways today (`PlayerCommand.h`, `IssueKind`): `Immediate`, which replaces the queue, or `Queued` (shift), which appends. This is a third kind, `Front`, for unit orders and for a factory's build queue alike, on a modifier of its own. It travels in a `PlayerCommand`, so it is lockstep-safe by construction, but it is a new command kind and therefore a replay-format and network-protocol change (`proto/network.proto`).

**The Ctrl hotkey block is done by one mechanism, not twenty features.** Most
of #131–#152 ask for a specific letter to select a specific kind of unit —
Ctrl+K for kbots, Ctrl+N for naval, Ctrl+Y for torpedo bombers. The original
does not have twenty selections: `0x4963e0` formats `"CTRL_%c"` and matches it
against the unit's FBI **Category** field (§74), and the shipped data defines
exactly six such tokens — `CTRL_W`, `CTRL_V`, `CTRL_F`, `CTRL_B`, `CTRL_R`,
`CTRL_P` — plus `CTRL_C` for the Commander. "Every other Ctrl+letter looks up
a category that no shipped unit has and selects nothing. A mod can invent
`CTRL_X` and the key springs to life." RWE implements the mechanism, so every
one of those letters already works for any data set that defines the token,
and none of them needs code. #131 (Ctrl+A), #145 (Ctrl+S), #152 (Ctrl+Z) and
#132 (Ctrl+D self-destruct) are separate features and are each implemented in
their own right.

**#126 (Ctrl+B cycles idle construction units) is refused, not deferred.** The
issue says so itself: "Functionality of modified OTA / demo recorder". In the
original Ctrl+B is the `CTRL_B` category selection — *all* construction units
at once — and that is what RWE does. Implementing the cycle would mean giving
a key a behaviour the original does not have and taking away one it does.
Recorded here rather than in §88 because it is a divergence from an *issue*
rather than from the binary. #133 (Ctrl+F cycles idle factories) is the same
mistake about the same mechanism and has the same answer.

**#125 is done in the part that is the original's.** Control groups are
implemented on the digits, the arrangement §75 decodes. The rest of that issue
is ProTA's rather than TA's — a sound on assignment, the squad number drawn
under the health bar, a factory adding what it builds to its own squad — and
is not planned.

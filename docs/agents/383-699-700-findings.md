## #383: profile meaning and the approved RWE translation

The mission's OTA `aiprofile` selects command-text data. The loader tries
that file first, and falls back to `ai\\default.txt` only if unavailable.
It then applies downloadable units' FBI `aiWeight` command text. The latter
has independently sticky weight and limit rules. The original does not
replace its computer-player strategy with an alternative AI engine because
a mission names a profile.

The established grammar is `plan`, `weight` and `limit`, as recorded in
`TOTALA-EXE-COMPUTER-PLAYER.md` section 123 and BT-128:

- Rules before the first `plan` are unconditional at ordinary initial setup.
  `plan` changes whether subsequent weight/limit rules apply at the chosen
  difficulty. `easy`, `medium` and `hard` correspond to difficulties 0, 1
  and 2. `any` is recognized only as the first argument, whereas difficulty
  words may occur at later argument positions.
- A rule subject is an exact unit name or a category. A unit-name match
  makes that property's assignment sticky. Later category rules cannot
  alter a sticky entry. Categories apply per member type, not a shared
  total across the category. `ALL` implicitly includes every unit type
  even when absent from its FBI category text (BT-78).
- A limit is an absolute per-type count threshold. Default -1 means
  unlimited; eligibility is strictly below the limit. Zero forbids the
  type; negative values other than -1 also block it. A missing numeric
  argument reads as zero. Existing owned quantities are not destroyed to
  satisfy a newly imposed limit.
- A weight starts at 100. The directive multiplies its current value by
  the specified floating multiplier, truncates toward zero and clamps to
  0 through 100. Thus 0.5 reduces a pristine type to 50, 2.0 cannot raise
  it above 100, and zero removes its positive contribution. This is a
  multiplier, not an absolute priority of 0.5 versus 2.0. A missing value
  reads as zero. Unit-name stickiness and category composition matter.
- Profile rules affect AI choices, not the human player's build menu and
  not already-created units. The FBI `ai_limit` key is separate and is not
  used as this profile's limit by the original.

The profile directive semantics above are conformance findings. Applying
them to RWE's own strategic planner, translating weights into its scoring,
and counting reserved queued production to avoid overshooting limits are
**RWE-original policy**, approved by the owner's option B. The original's
economy score and weighted random selection have no direct counterpart in
that planner; do not claim identical build sequences or original AI parity.
Keep the translation deterministic and record its exact policy in the
existing divergence/compatibility register. These findings do not prescribe
new RWE planner structure or code.

A shipped-data acceptance check should use mission-selected profile data at
all three difficulties, constructor limits, an explicitly forbidden unit,
category and direct-unit overlap, and two choices with unequal effective
weights. Test the existing classic AI separately from the RWE translation.
BT-128's older caveat about malformed single-argument command dispatch is
not resolved by this inspection; well-formed shipped rules and their parsed
values are the primary oracle. A retained missing-value rule should be
reported as static accessor evidence rather than a runtime observation.

## #699: death and replacement

The original rule numbers and lobby cycle are 0 Continues, 1 Game Ends,
2 Deathmatch, then 0. Wire options 0x08 and 0x10 describe values 1 and 2;
neither means value 0. RWE's pre-existing enum numbering is different and
must not be treated as the original's on-wire value.

Continues leaves other units alive after the side's commander dies. Game
Ends and Deathmatch both apply the player wipe when that side's commander
dies. The wipe is **30000 direct damage with death cause 3**, rather than
ordinary player self-destruct's cause. Locally simulated human/computer
units take that damage; the remote-unit presentation branch detonates its
secondary weapon and receives cause 3. This is distinct from killing every
unit through an unqualified quiet-removal path. Follow existing documented
damage/death semantics for cause 3, including casualties still processing
their destruction. Do not substitute cause 9 factory-held-product cleanup.

Defeat is still the player's zero live-unit count, observed by the slower
result pass. The first positive observation installs 4; the next five
positive observations reduce it through 3, 2, 1, 0 and -1. At 30-tick
intervals that is 150 ticks after first detection. A false observation
neither clears nor advances the stored number. A subsequent true
observation resumes its progress. Non-campaign polling asks defeat before
victory; a simultaneous wipe therefore has no draw result (BT-191).

Deathmatch replaces the defeated local human's commander at expiry instead
of ending the game. At this location the original creates a replacement for
the local player only; it does not loop over locally hosted computer
players. Extending automatic replacement to every RWE computer seat is a
lockstep gameplay policy, not a literal port of this branch. It is sensible
for a unified mode, but must be recorded as such.

Replacement uses the side data's commander name and up to 9999 candidate
positions. Each candidate has independently drawn integer X and Z. For an
axis extent W in world units, the integer margin is floor(W / 10), and the
range is W minus twice that margin. The coordinate is margin plus a draw
in [0, range - 1]. X is drawn before Z on each candidate. Coordinates enter
the 16.16 position with height initially zero. Creation performs its normal
placement/height initialization. There is no hard-coded commander name.

The nine placement probes use offsets **minus the map's cell count, zero,
plus the map's cell count in WORLD UNITS**, separately on each axis. The
extent fields are global offsets +0x14233 and +0x14237. The corresponding
world extents +0x14223 and +0x14227 are sixteen times those cell counts.
Consequently, this is a widely spaced 3 by 3 neighborhood: a 256-cell-wide
map has X probe offsets -256, 0, +256 world units (16 cells), not -16, 0,
+16 and not one commander footprint. Each probe is converted to a cell by
division by 16 with floor semantics; **no footprint-centering subtraction**
is applied at this call. The cell is the probe's footprint origin. Every
probe must pass. The mobile placement test rejects out-of-bounds footprints,
occupied cells, steep features, unsuitable water depth and slopes.
The central candidate must also have no feature, independently of those
nine footprint tests. On a lava map its sampled ground mean must be
strictly above sea level. After exhausting all 9999 candidates, the original
still attempts creation at the final candidate. It does not substitute a
start position or enlarge the search. Its returned pointer is unchecked;
RWE should handle failure safely without claiming that robustness is an
original feature.

The draw routine's positive range is exclusive at the upper end. Range
less than two returns zero **without advancing the seed**. Its 32-bit
unsigned arithmetic is: q = floor(seed / 127773); new seed is
seed times 16807 minus ((q times 2147483648) minus q), modulo 2^32;
if its signed interpretation is nonpositive, add 2147483647 modulo 2^32.
The result is the updated unsigned seed modulo the range. For ordinary
valid Park-Miller seeds this is the familiar modulus 2147483647 sequence.
Using RWE's existing generator instead is an explicit RWE lockstep
adaptation; seed-equivalent candidate parity must not then be claimed.

The new commander receives the host's starting resource amounts (the
stored lobby units multiplied by 100). Starting storage bonuses are reset
from these settings. Energy and metal are credited through the commander's
account; credits to a computer are scaled 0.5 easy, 0.7 medium and 1.0
otherwise. Human credits are unscaled. This is an additive starting credit,
not a general reset of all lifetime player statistics. Sight is recalculated
and the local camera focuses the replacement.

### Respawn resource/storage clarification (same reference revision)

The storage helper at **0x496E90** sets bit 0 of the player's flag word at
offset +0x149 and assigns the storage bonuses at +0xDC (energy) and +0xE0
(metal). Each bonus is **max(200, the corresponding host starting amount)**,
where the host setting has already been multiplied by 100. These are
unscaled storage amounts: easy/medium difficulty does not reduce capacity.
This storage reset takes place after the new unit has been created.

The helper neither clears nor overwrites the player's current energy or
metal stockpile. The replacement path does not reinitialize the player,
its accumulated statistics, debt, or its current stockpile. The commander
receives the new starting credit in its production account, which is
pooled with any retained player stockpile during the next economy settle.
Finished units' FBI storage is added on top of the player's base bonus.
Commander FBI storage is not replaced by the bonus in the original.
The settle then pays outstanding debt/demand and caps the remainder at the
recomputed storage in the ordinary manner, recording any excess.

The original applies difficulty scaling at the **credit to the production
account**, exactly once: start amount times 0.5/0.7/1.0 for a locally
simulated computer, or the full amount for a human. The settle at 0x401360
adds the already scaled production and applies **no second multiplier**.
The replacement credit consequently contributes to produced/income
statistics just like other positive production credits. Production by the
replacement commander in the same second is a separate ordinary credit.

For the current RWE representation, the corresponding facts mean the
base-storage-present state becomes true at replacement, and the two base
amounts take the host start settings with the 200 floor. Leaving that state
false would retain the older skirmish convention in which the commander
itself carries the starting storage; it would not implement this original
respawn setter. Retaining the existing player stockpile is correct. RWE
currently multiplies pooled production at settlement rather than each
individual credit; therefore supplying an unscaled starting credit to that
existing path yields one multiplier, while pre-scaling the credit as well
would apply it twice. These statements describe arithmetic and observable
resource treatment, not a required implementation method.

As an arithmetic example excluding ordinary unit production and debt, host
start metal 1000 with retained stockpile 100 gives an unscaled base capacity
1000 plus finished-unit FBI storage. A human's replacement credit is 1000;
an easy computer's is 500. Before the capacity clamp those yield 1100 and
600 respectively. This is an illustrative calculation, not a shipped-data
or executed original-game test.

In multiplayer Deathmatch the allied-victory test at 0x490080 always returns
false, and the no-combat-human fallback at the end of 0x464F80 is disabled.
Therefore an empty enemy roster during the respawn wait must not cause
victory. The skirmish victory routine is separately dispatched and does not
contain that early Deathmatch guard; applying the endless-respawn policy to
RWE skirmish as well is a deliberate unification, not established retail
skirmish parity. Campaign mission conditions remain a separate authority.

## #700: eligibility and choice

At ordinary defeat expiry, continued watching is considered only in a
multiplayer game with no local rejection/removal reason. Eligibility is
the host record's **low-byte bit 0x80 at offset +0x9B**, OR the continued
existence of a locally simulated computer player. This host permission is
different from the local player's low-byte bit 0x40, which means the seat
is already watching. The local host/guest identity alone does not imply
permission. A locally hosted computer is active, simulated on this machine,
not the sentinel index 10, and either still has units or has not yet created
any. Defeated computers with a nonzero lifetime created count do not qualify.

Eligible conversion sets the local seat's watching bit, clears map flags
bits 0 and 1, recalculates sight and broadcasts the updated player info.
This happens **before** presenting a choice. The map-bit change is local
presentation; it does not revive the player or change ownership/alliance.
The two bits govern ordinary mapped/LOS restriction paths; the remaining
sight masks are still used, so this finding does not establish unrestricted
omniscient visibility for every rendering subsystem.

**No surviving hosted computer:** show the translated Yes/No dialog with
the title `You're out!  Continue Watching?`. Yes broadcasts and continues;
No requests exit/end flow. **Hosted computer remains:** the player is
placed in watching automatically; where combat humans remain, show the
explanatory message that exiting will terminate hosted computer players.
This is the opposite of the old BT-89 statement. If no combat human remains,
there is no explanatory message; the ordinary no-human end fallback may
finish the game. Combat-human counting excludes watching seats and excludes
computer players even though those computers can still own units.

Ineligible or rejected seats enter the existing end flow. No option here
reverses losses, restores a commander, changes player economy or cancels
the defeat. An already-watching seat skips ordinary defeat re-polling while
the match can continue toward victory/end. Deathmatch takes replacement
instead of this watching branch.

The exact persisted default for the host's permission was not established
by this focused inspection; retain an explicitly documented RWE default
instead of attributing one to the original. A new launcher/lobby option
must carry the host's choice to all peers; a local preference cannot decide
deterministic elimination state.

## Countdown scope and lockstep translation

The original owns **one machine-global signed countdown**, initialized to
-1. Its nonnegative value inhibits all economy settlement performed on
that machine, including locally hosted computers, while remote machines
own their own counters/economies. It is not one global counter shared
between peers and is not one counter per player. Expiry leaves the word at
-1; neither successful respawn nor conversion to watching assigns it again.
Economy becomes eligible immediately in the same per-player pass, with
normal active/unit-count guards still applying. A false result before
expiry does not unfreeze an already nonnegative counter.

That owner-authoritative quirk cannot be copied blindly into RWE's shared
simulation: a local human's countdown must not freeze different AI seats on
different peers. A deterministic per-seat elimination/respawn countdown and
per-seat economy freeze is an appropriate **RWE-original lockstep
translation**, subject to documenting the departure in the existing
divergence register. Keep final match-result countdown, local dialogs and
camera state distinct in their respective roles. New future-affecting
per-seat state requires the usual save/hash/replay/dump treatment.
